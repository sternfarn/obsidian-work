## Files

### BEHAVIOR.md

A complete external contract

- Every entry point (CLI flags, functions, endpoints) with exact inputs/outputs.
- Every file, network, DB, and env-var interaction.
- Every observable edge case: empty input, malformed rows, encoding,
  duplicates, ordering guarantees, float/rounding behavior, timezone
  handling, what happens on partial failure.
- Exit codes, log output others may depend on, output file formats.

### QUESTIONS.md

A list of every piece of code where the *reason* is not obvious from the code itself — special cases, magic numbers, retries, sleeps, defensive branches, odd orderings. For each,
give your best guess and classify it:

- ESSENTIAL (a real business/data rule) 
- ACCIDENTAL (a workaround for how the code was structured) 
- UNKNOWN (I need to ask Stefan).
 
Check `git log`/`git blame` on those lines for clues first.

### QUESTIONS.md

and answer. This is the step that stops the rewrite from silently deleting a bug fix you made at 2am in 2021 — and equally, stops it from lovingly preserving a workaround that only existed because of the old structure.

## Phases

> [!info] Every phase a new session.

### Phase 1 — Freeze behavior in tests, against the old code

Write characterization tests for the current implementation. Goal: if I
rewrite this from scratch, these tests tell me whether I broke anything.

- Use real inputs from dir plus edge cases from BEHAVIOR.md.
- Golden/snapshot outputs generated by running the CURRENT code.
- Test only the external contract, never internal functions — the
  internals are all going to be deleted.
- 
Also write a differential harness: run old and new implementations on the
same input set and diff outputs byte-for-byte.

This is what buys you the freedom to be radical later. Without it, every refactor is a leap of faith and you'll end up conservatively porting the old shape.

### Phase 2 — Design, no code

Given BEHAVIOR.md and my answers in QUESTIONS.md, propose 2–3 different
architectures for a clean rewrite. For each: module layout, the core data
types, where I/O lives, and what gets *dropped* from the old design and why.
Explicitly call out where the old structure forced complexity that
disappears under your design. No code yet. Recommend one and say why.

You read this in five minutes and either recognize your own instinct or find something better. Cheapest possible place to disagree.

### Phase 3 — Rewrite, in a fresh session

This is the key trick: start a new session where the old source is not the primary context.

Implement the design in DESIGN.md from scratch in `<new dir>`.
Sources of truth: BEHAVIOR.md, QUESTIONS.md, DESIGN.md, the test suite.
The old code at `<path>` is reference-only — consult it to check a *rule*
you're unsure about; do NOT port its structure, naming, or con
If your implementation ends up shaped like the old one, that's a smell.

**Constraints**

- Full type hints; `mypy --strict` clean; ruff clean.
- Pure functions in the core, all I/O at the edges.
- No bare/broad except; catch specific exceptions only where you can act.
- No module-level mutable state, no global config object.
- Anything from QUESTIONS.md marked ESSENTIAL must survive and
  named test with a comment saying why it exists.
- Anything marked ACCIDENTAL must NOT be carried over.

Work one vertical slice at a time. After each slice: run the tests and
the differential harness, and commit. Stop and ask me if a golden test
fails in a way you think is the *old* code being wrong.

### Phase 4 — Adversarial pass

Fresh session again: /code-review high, plus one explicit prompt: "Where did this rewrite reintroduce complexity that BEHAVIOR.md doesn't justify? Where are abstractions with a single caller? Where is a class that should be a function?" Claude reviews its own output far better when it isn't in the mindset of defending it.

The two things people get wrong

Wanted changes vs. frozen behavior. Write a short CHANGES.md first: "these behaviors I want changed / dropped / added; everything else is frozen." Without it, the model either preserves bugs faithfully or fixes them silently — both bad, and you can't tell which happened.

Scope of the frozen contract. Freeze the external contract only. If you freeze function signatures or module names, you've pre-committed to the old design and you'll get a lipstick refactor.

# Answer from how I understood the plan and how I would have approached it

Who writes what

There's a clean rule that resolves most of your questions:

Claude writes everything derivable from an artifact. You write only what exists nowhere but your head.

- BEHAVIOR.md → Claude. It's derivable from the code. You read and correct it.
- QUESTIONS.md → Claude raises the questions, you answer them. Claude is much better than you at spotting "why is there a sleep(2) here" because it has no memory of writing it. You are the only possible source for the answer.
- CHANGES.md → you. Nothing in the code says what you wish it did.
- DESIGN.md → Claude proposes 2–3, you pick. That's the point of Phase 2.

So: not "do we iterate" as a general practice — the iteration is specifically you reading Claude's extraction and pushing back. Your knowledge entering the loop is the whole value of these documents. Claude re-reading its own document adds much less.

Order, and session boundaries

Your instinct that BEHAVIOR.md comes first and deserves the most effort is right. Two adjustments:

Write a rough CHANGES.md first — 20 minutes, bullet points, "I want X to change, Y to be dropped, everything else frozen." It's cheap and it changes how you read BEHAVIOR.md. Refine it after Phase 1.

BEHAVIOR.md and QUESTIONS.md are one session, not two. They come from the same read of the same code. Splitting them means the second session pays full price to rebuild context it just threw away.

That's the actual rule for session boundaries — not one per file. Start a new session when the context you want changes, for one of two reasons:

1. Contamination: in Phase 3 the old code's shape is actively harmful, so it must not be in context.
2. Stance: in Phase 4 the author defends its work, so the reviewer must not be the author.

"One session per file" is cargo-culting the shape of that rule without the reason.

Your critique pipeline

▎ session writes BEHAVIOUR.md → session criticises → session merges → session reviews

Here's the problem, and it's the same thing you already noticed about yourself:

▎ i also found myself iterating over md files without hardly reading it

A critique loop with no external ground truth converges on plausibility, not truth. Round three sounds better than round one and may be less accurate. You've built a machine that produces confidence without producing correctness — and because you're not reading the output, you can't tell the difference. That's the most dangerous possible failure mode for the kind of work you do, where data has to flow with high accuracy.

The fix is not a better critic. It's replacing opinion with a signal that can fail:

- Instead of "criticize BEHAVIOR.md" → "for every claim in BEHAVIOR.md, write a test against the old code that proves it. Mark any claim you cannot prove as UNVERIFIED." Now the critique either produces a passing test or an admission. Both are useful; neither is vibes.
- Then: run those tests under coverage against the old code. Uncovered lines are undocumented behavior. That's a completeness metric with a number on it, instead of an LLM saying "this looks comprehensive."

That's the same idea as the best line in your instruction doc — "checkable rules instead of adjectives" — applied one level up, to the documents themselves. A critique session is an adjective. A failing test is a checkable rule.

Should you automate it with claude -p?

The instinct is right, the target is wrong. Automate loops that have a pass/fail exit condition; never automate loops whose exit condition is "the doc is good now."

Good candidates for a claude -p harness: run the differential harness → if outputs differ, feed the diff back → fix → re-run, until byte-identical. Or: mypy/ruff/tests until clean. Those terminate, and they terminate on something real.

A document-critique pipeline doesn't terminate. It just burns tokens until you get bored, and you can't tell whether round five was better than round two.

Also, practically: don't build this before you've run the process by hand once. Automating a workflow you haven't executed yet means you're optimizing a guess about where the pain is. Run Phase 1 manually, notice what you did five times, automate that.

Where the real leverage is

You asked whether AI is more powerful than "sometimes asking questions." It is — but the unlock isn't more prompting, more sessions, or more critique. It's this:

Give Claude something it can check itself against, then let it iterate unsupervised. Every hour you spend building executable ground truth — the characterization suite, the differential harness, a corpus of real production inputs, mypy --strict, coverage — buys you unattended, verifiable progress. Every hour spent on another critique pass buys you a document that sounds better.

Concretely, for your rewrite: sprint to the point where you have a differential harness running old vs. new on real report data. Before that line, everything is speculation. After it, everything is checkable, and you can be genuinely radical in the rewrite. That harness also outlives the project — it's reusable infrastructure for exactly the kind of accuracy-critical data flow you work on.

Two more things worth knowing:

- You have to read BEHAVIOR.md and QUESTIONS.md. They're the only two places your knowledge enters the process. Skimming them isn't a shortcut, it removes the thing that makes the method work. Time-box it: if you're more than a couple of days into document production without a running test, the process has become the project.
- An alternative shape, if the program is a pipeline: skip the big-bang rewrite. Build the new one behind the same interface and run both in shadow mode on live inputs, comparing outputs, until the new one is boring. Same differential idea, but you get confidence continuously instead of at the end.

On the MCP course — worth doing, but note it's a different axis. MCP is about giving Claude access to your systems. What we're discussing is giving Claude verification. For a rewrite, verification is the lever; MCP becomes interesting later, when you want Claude operating inside the actual Nexxar workflow.

One thing that would change my advice: how big is the program? A 500-line script doesn't justify this ceremony — write the characterization tests and just rewrite it. 10k lines with five years of accumulated client edge cases and the full method is about right.
